## Главный план: единый проект шаблонов

Один GitHub-репозиторий хранит много переиспользуемых дизайнов. Каждый клиент выбирает один дизайн; его данные хранятся отдельно от публичных demo-шаблонов.

Целевая структура:

```text
# Публичный GitHub-репозиторий
templates/
  1/
    template.json          # metadata, статус, preview, возможности дизайна
    demo.json              # только обезличенные demo-данные
  <следующий-template>/
shared/
  schemas/client-data.schema.json
catalog/
public/catalog-template/manifest.json

# Приватно, вне публичного Git
~/Projects/invitation-client-vault/
  <client-id>/
    client.json            # реальные данные одного клиента
    assets/                 # согласованные фотографии/декор
```

### Правило готовности шаблонов

У каждого шаблона есть явный статус в metadata/manifest:

- `draft` — шаблон в разработке. Он остаётся внутри проекта, но не попадает в публичный каталог и его нельзя выбрать для создания приглашения.
- `ready` — шаблон закончен. Он автоматически появляется в каталоге с производной карточкой/preview из его demo-данных и становится доступен для создания нового приглашения.

Это правило является частью главного плана: готовность управляет отображением, а не ручное копирование карточек или ссылок.

## Единый формат данных клиента

В `shared/schemas/client-data.schema.json` фиксируется общий формат, независимый от дизайна:

```text
couple, event, venue, schedule, rsvp, contacts, gallery, theme
```

- Первые семь блоков — реальные сведения клиента.
- `theme` — только разрешённые настройки выбранного шаблона: например, цветовая схема или вариант декоративного блока.
- Каждый шаблон объявляет, какие поля `theme` он поддерживает. Персональные данные не смешиваются с кодом шаблона.
- В public Git лежит только `demo.json`; настоящий `client.json` и assets — только в `~/Projects/invitation-client-vault/<client-id>/` или позднее в отдельном private-репозитории.

## Skill: адаптация шаблона под клиента

Создаём отдельный локальный skill `invitation-client-adaptation`. Он будет обязательным способом работы с новым заказом:

1. Принять только выбранный `ready`-шаблон.
2. Создать приватную папку клиента и `client.json` по общей schema.
3. Проверить обязательные данные, ссылки, время, карту и assets.
4. Подставить в выбранный шаблон другие тестовые данные через `client.json`: имена, дату, время, карту, фотографии и RSVP — без ручной правки HTML шаблона.
5. Сгенерировать и проверить локальную preview-приглашение в браузере на телефоне.
6. Зафиксировать результат QA и только затем оформить повторяемые действия в skill.
7. Подготовить публикацию, но не выполнять GitHub/Vercel-действия без отдельного разрешения.

Skill создаётся после того, как schema и первый ручной проход адаптации успешно проверены: тогда в нём будут реальные, а не предположительные команды и проверки.

## Следующие этапы

1. Ввести multi-template структуру и metadata каждого шаблона.
2. Добавить статус `draft`/`ready`; валидировать все шаблоны и публиковать в manifest только `ready`.

5. Выполнить один ручной безопасный проход «ready template → private client config → локальная preview».
6. На основе этого прохода создать и проверить skill `invitation-client-adaptation`.
7. Собрать Vite, Astro и Next; проверить в браузере: `draft` скрыт, `ready` виден, а клиентские данные корректно рендерятся.
8. Затем — owner-admin, потом автоматизация.
9. После отдельного подтверждения: коммит, GitHub-публикация и Vercel-деплой.

## Подробный план выполнения и доказательств

Это рабочий источник правды для следующей сессии. Выполнять строго по порядку: ограниченная реализация → технические проверки → браузер → визуальная проверка на мобильных ширинах → отчёт с фактическими результатами. Успешный build сам по себе не завершает этап.

### Неподвижные правила

1. Public repository содержит только код шаблонов, metadata, demo-данные и безопасные preview.
2. Реальные имена, телефоны, RSVP, фотографии, ссылки и assets хранятся только вне public Git: `~/Projects/invitation-client-vault/<client-id>/`.
3. Выбрать для клиента можно только template со статусом `ready`.
4. Только имена пары автоматически создаются как PNG. Это PNG/RGBA с прозрачным фоном.
5. Дата, время, зал, адрес, карта, программа, текст, контакты, RSVP и всё иное — live HTML/CSS-текст в DOM.
6. При адаптации клиента нельзя вручную менять HTML/CSS template: меняются private config и разрешённые assets.
7. Commit, push, Vercel link/deploy и доменные операции — только после отдельного прямого разрешения.

**Реализация:** создать `templates/<template-id>/`; перенести `1` в self-contained формат с `template.json`, `demo.json`, исходниками и preview. Обязательная metadata: `id`, `name`, `category`, `status`, `preview`, `supportedBlocks`.

### Этап 2 — readiness и generated manifest

**Реализация:** schema metadata и discovery всех templates. Допустимы только `draft` и `ready`. Manifest строится только из `ready`; у `ready` обязателен preview. Дубликаты `id`, неверный статус и schema errors останавливают генерацию с ошибкой.

**Доказательства:** тестовый `draft` отсутствует в manifest; отдельно проверены реальные ошибки: duplicate id, неверный status, ready без preview; после исправления получен валидный manifest JSON.

### Этап 3 — каталог только из manifest

**Реализация:** подключить `catalog-next` к generated manifest и убрать ручные параллельные metadata-списки. Карточки, фильтры и выбор template читают только manifest.

**Доказательства:** локально виден `1`, draft отсутствует; изменение metadata ready template после генерации меняет карточку в браузере; сделаны проверки на телефонных ширинах.

### Этап 4 — общая client-data schema и private renderer

**Реализация:** создать `shared/schemas/client-data.schema.json` с блоками `couple`, `event`, `venue`, `schedule`, `rsvp`, `contacts`, `gallery`, `theme`. Добавить validation private `client.json` и renderer, который выбирает ready template и подставляет данные без изменения исходного HTML/CSS. День, месяц и countdown вычисляются из `event.date`/`event.time`.

**Доказательства:** создан test-only private instance; успешная validation и минимум три реальные ошибки данных проверены; `git status` и public output подтверждают отсутствие private values/assets.

### Этап 5 — PNG-имена и live text

**Реализация:** генератор PNG только из `couple.groomName` и `couple.brideName`, связанный с renderer. Другие поля нельзя превращать в изображения.

**Доказательства:** длинные тестовые имена создают новые PNG; технически проверены PNG/RGBA и alpha=0 у фона; на mobile имена не обрезаны. После смены даты, времени, зала, адреса, карты, текста и контактов DOM подтверждает, что эти значения — text, а не images.

### Этап 6 — полный ручной клиентский сценарий

**Реализация:** воспроизводимый flow: `ready template → private client.json + assets → local preview`.

**Доказательства:** выбран ready template из manifest; создан отдельный private test client; все поля и assets валидированы; local invitation открыт. В браузере сверены имена, date/time, venue, address, map URL, text, photos, RSVP и countdown. Проверены desktop, несколько mobile-ширин, консоль и интерактивные ссылки/форма. Создан QA record без реальных персональных данных.

### Этап 7 — skill `invitation-client-adaptation`

**Предусловие:** этап 6 доказан фактическими результатами.

**Реализация:** создать skill только из реально сработавших команд: выбор ready template, private instance, validation, assets, генерация имён PNG, local preview, visual QA, QA record и safety check.

**Доказательства:** повторить workflow только по skill с третьим набором вымышленных данных. Если данные заменились без правки HTML/CSS и QA прошла — skill готов.

### Этап 8 — сквозная QA

**Проверка:** build затронутых приложений, browser runtime без ошибок, mobile screenshots, manifest, draft/ready, map, countdown, RSVP, images, live text и отсутствие private data в public Git. В отчёте явно разделять пройденные и непройденные пункты.

### Этап 9 — owner-admin

Начинать только после этапов 1–8. Owner-admin: выбор только ready template, создание private invitation и редактирование client data. Перед реализацией согласовать отдельный план и модель данных.

### Этап 10 — automation

Начинать только после owner-admin. Автоматизировать validation, preview, manifest, build, QA-preparation и handoff. Автоматизация не публикует проект сама.

### Этап 11 — публикация

Только после отдельного явного сообщения пользователя: commit, GitHub push, Vercel deploy, browser-проверка реального production URL и отчёт с URL.
